## 1. 修改现有需求

先建立受影响清单，再编辑：

| 类型 | 处理 |
| --- | --- |
| 业务基线 | 更新跨页面统一结论 |
| 页面需求 | 更新功能、规则、交互、异常和展示口径 |
| 中间原型 | 仅在交付模式包含原型且本次结论需要交互验证时修改 |
| 关键逻辑 | 多页面共享状态、权限或顺序发生变化时更新 |
| 项目总览 | 范围、模块、页面或走查路径发生变化时更新 |
| 更新记录 | 评审后变更且项目要求维护时追加 |
| 验收记录 | 实际完成浏览器或 Figma 验收后更新 |

本次页面修改的右侧说明直接列修改项，不显示九段式章节标题和序号；已有完整需求作为基线保留，按需同步受影响内容，不删去未变更章节来制作增量说明。

不要把“搜到关键词”直接等同于“需要修改”。阅读上下文，区分历史说明、当前规则、示例数据和真实交付内容。

左侧导航按 `delivery-modes.md` 的固定格式维护：整份需求标题、分组与组内页面、底部创建时间和更新时间。新增/移除页面时同步整份需求的导航；实际修改后保留创建时间，并将各页面的需求级更新时间同步为本次修改日期。只读检查和打开页面不更新时间。导航时间不替代评审后的需求更新记录。

## 2. 更新记录

- 需求梳理阶段默认不创建更新记录。
- 评审基线确认后，第一次实际变更时创建更新记录和项目维护约定。
- 同一天的多次修改进入同一日期分组；跨天新增日期分组。
- 每条记录包含变更类型、调整内容和影响范围。
- 只记录已经落地的修改，不记录计划、讨论或失败尝试。
- 修正文案时不要回写或删除历史记录，除非用户明确要求维护历史记录本身。

## 3. 静态检查

运行：

```bash
node scripts/validate_project.mjs /absolute/path/to/project
```

检查范围：

- HTML 中重复 `id`。
- 本地 `href`、`src` 和表单 `action` 是否存在；指向 HTML 的同页及跨页锚点是否存在。
- 无 `src` 的普通及 `type="module"` JavaScript 是否能解析；只检查语法，不执行代码或解析模块依赖。
- 使用 skill 模板的页面是否保留导航、中间区和需求区。

模板页面交付前加 `--strict`：

```bash
node scripts/validate_project.mjs /absolute/path/to/project --strict
```

严格检查仅作用于带 `data-prd-page` 的模板页面：识别模板占位标记、占位样式和“待补充”段落。页面型文档按 `data-page-type` 检查 `#spec`：`new` 必须九段齐全且有序；`change` 至少包含一个非空修改项（`li`），不包含正文大标题（`h2`）。未标类型的旧页面按 `new` 处理。功能／规则编号不必填写；全新页面的功能／业务规则章及修改页面正文的表格首列若使用 `F-`／`R-` 编号，检查其原有格式 `F/R-[页面缩写]-[两位序号]` 和重复，不把普通对比表首列当作编号。旧总览与规则文档不套九段式。默认模式允许草稿占位，严格模式发现上述问题返回非零退出码。

人工复核全新页面的九段式章节大标题和章节序号均可见，正文只写最终逻辑，无“已确认”等过程标签；修改页面直接列修改对象与修改后的要求，不显示分类大标题或章节序号，不展开旧方案或附加未变更声明。检查正文之外的待确认问题是否阻断交付；结构检查通过不等于逻辑已经确认。

交付前逐条检查完整句子，尤其是逗号、分号后的否定尾句（如“不……”“无需……”“不附加……”）：

- 前文已限定范围、后文只是重复排除时，删除排除尾句；用户未提出的假设性排除项也不写入正文。
- 含独立业务信息时，将必要规则合并为正向的适用条件、展示内容或操作结果；无法等义改写时才保留必要否定表达。
- 对照原始要求核对条件、影响、限制、异常与结果，确保没有丢失逻辑或扩大、缩小范围。否定词仅用于定位复核，不作自动删除或验收失败的依据。

检查器面向静态 HTML，不执行脚本；动态生成的锚点、路由、外部脚本、业务语义、编号跨页一致性和章节内容质量仍需项目检查或浏览器验收。已有项目未使用模板标记时，不强加模板结构检查。

维护 skill 后运行 `node --test tests/scripts.test.mjs`。以上命令路径均相对于 skill 目录；在其他工作目录执行时使用脚本的绝对路径。

## 4. 原型验收

按风险选择验收深度：

- 文案和说明修改：静态检查、全文检索旧口径。
- 页面结构或状态修改：实际打开页面，验证目标状态和关键动作。
- 跨页面业务修改：走查完整入口、跳转、返回、失败和恢复路径。
- 响应式或 Figma 还原：至少检查目标桌面视口和移动视口，并保留截图证据。

验收关注：布局稳定、文本不遮挡、操作可达、动态内容不引发布局跳动、弹层可关闭、失败后有下一步、控制台无新增错误。

原型区另检查：无额外“原型说明”或演示限制提示块（限制另记在交付说明或验收记录中）；外部工具栏与产品 UI 分离；标题对应当前页面；状态控件仅在需要时出现且能切换真实内容；手机／网页外框符合项目基准；拖动分栏及窄屏下等比预览、不横向溢出；长内容在原型内滚动。不要将内部业务结构统一成固定模板，也不要用预览缩放代替产品响应式验收。仅需求说明模式不显示工具栏或外框。

## 5. Figma 同步

先读取现有需求和原型，再读取 Figma。建立三类差异：

- 视觉差异：尺寸、颜色、排版、资源和布局，可按设计稿处理。
- 交互差异：入口、动作、状态、跳转、反馈和恢复，必须确认。
- 业务差异：资格、规则、范围和口径，必须确认。

应用视觉更新后重新验证原有交互和状态。不要用静态截图替代可操作原型，也不要因为 Figma 未展示某个异常态就删除异常态。

## 6. 完成交付

最终说明包含：

- 修改了什么及核心结论。
- 哪些关联页面已同步。
- 运行了哪些静态和浏览器验证。
- 哪些冲突经用户确认。
- 哪些验证因权限、环境或缺少依据未完成。

不要声称未实际执行的浏览器或 Figma 验收已经通过。
