# 右侧需求说明

右侧只约束页面需求，按“全新页面 / 页面修改”区分写法。业务规则文档、项目总览可作为独立项目资产，沿用项目或用户约定，不在这里规定另外两种结构。

## 1. 总体要求

**逻辑完整、语言简练。只写影响理解、实现和验收的信息，同一规则只写一次。**

- 默认使用短句和列表；只有需要对比多个对象或条件时才使用表格，不强制表格列数。
- 不重复页面名称，不强制英文标识、优先级、用户故事句式或功能／规则编号。需要引用、追踪时才编号；已有有效编号保持稳定。
- 引用既有规则时提供可定位的章节或链接，不全文抄写。不要用“优化体验”“友好提示”“适当处理”等空泛措辞代替具体行为。
- 不按字数或条数凑内容，不罗列无关状态，不把原型中清楚可见的 UI 再写成清单。
- 正文直接说明最终要求；确认记录、方案讨论和变更历史如需保留，放在独立记录中，不混入页面需求正文。
- 关键未决逻辑单独列为待确认问题，放在正文之外的澄清记录或交付说明中，不自行编造确定结论；阻断实现或验收的问题解决前，不将相关逻辑视为完成。
- 正向写清适用范围、展示内容和操作结果即可，不追加“不要……”“不附加……”“不会……”“无需……”等重复排除项。该规则同时适用于全新页面和页面修改，包含逗号、分号后的尾句；前文已限定范围时，不再列举范围外的情况，也不补充用户未提出的排除要求。
- 必要的权限、限制和异常优先写成明确条件或状态，例如“仅登录用户可提交”。只有正向改写无法准确保留业务含义时才保留必要的否定表达；“属于业务限制”不能作为保留重复排除项的理由。逐条核对原意，不按否定词机械删句，也不为改写而擅自增加“仅”等范围限制。

类型按需求本身判断，不按本轮是否编辑了文件判断。精简文案、补充逻辑或优化已有全新页面文档时，保持其全新页面类型和九段式标题；隐藏章节标题的规则仅作用于页面修改类型，不批量应用到同一项目的其他页面。

## 2. 九段式章节

全新页面必须按以下顺序显示九段式章节大标题和章节序号，不只是内部核对；仅页面修改类型用这些维度内部核对逻辑，正文直接列修改项。既有全新页面标题略有差异时沿用原命名，不机械改名。

| 章节 | 写什么 | 不重复什么 |
| --- | --- | --- |
| 一、页面概述 | 用途、适用用户、必要入口 | 页面标题和无意义的基础信息 |
| 二、用户目标 | 一句话说明用户要完成什么 | 固定“作为…我希望…以便…”句式 |
| 三、功能说明 | 按“条件 → 操作 → 结果”写清功能 | 每项功能的优先级和重复的规则说明 |
| 四、页面元素与状态 | 原型无法直接表达的显示条件、默认值、必要状态 | 原型已清晰展示的按钮、图标和布局 |
| 五、业务规则 | 资格、限制、计算、业务排序、互斥、时效 | 已说明的普通功能操作 |
| 六、交互与跳转 | 目标页面、返回行为、内容保留／重置、特殊交互 | 功能说明中已写明的普通点击结果 |
| 七、数据与展示 | 展示内容、默认值、展示排序、格式、缺失处理 | 技术字段或已写清的业务排序规则 |
| 八、异常与边界 | 本页适用的异常条件、用户反馈和恢复方式 | 与本页无关的通用异常清单 |
| 九、文案与补充要求 | 必须明确的提示文案、隐私和其他约束 | 第七段已说明的展示规则 |

每条规则放在最适合的章节；其他章节需要时引用即可。精确文案在其对应逻辑处已经写明时，第九段不再复述。

## 3. 全新页面

- 标明“全新页面”，保留并显示九段式章节大标题及“一、”至“九、”的章节序号，再逐项核对，完整说明入口、操作、规则、结果及适用的异常与恢复逻辑。
- 直接写功能、规则、交互、状态和异常处理，不添加“已确认”“经讨论确定”“最终决定”“本次明确”等过程标签，不叙述方案讨论经过或被否决的方案。
- 某段确无补充时写“无补充”或“不适用”，不为填满章节虚构需求；关键逻辑未知时另列待确认问题，不能用“不适用”掩盖缺失。
- 仅需求说明模式没有原型，需用文字补足理解页面所必需的元素和状态；仍不必逐项罗列无关 UI。

## 4. 页面修改

- 标明“页面修改”，用一句话概括本次变更。
- 保留页面名称；正文直接列修改项，不显示“三、功能说明”“六、交互与跳转”等九段式大标题和章节序号，也不新增“功能修改”“交互调整”等分类大标题。九段式仅用于内部检查遗漏。
- 使用无序列表或从 1 开始的连续修改项列表，每项可用加粗短语标识修改对象，不另起章节标题。HTML 模板使用 `ul` 或 `ol` 中的 `li`；摘要不能替代实际修改项。
- 每个修改点直接写清：**修改对象、修改后的行为或规则，以及必要条件、影响与异常**。默认只写修改后的要求，不展开修改前的情况，不用“不是……”“不再……”“不要……”衬托新方案。
- 删除、取消、隐藏也是明确的修改要求，直接写“移除分享入口”“取消二次确认”“隐藏已过期活动”，不绕着旧逻辑解释。
- 未修改内容不展开，也不附加“其他逻辑保持不变”“未涉及行为沿用基线”等声明。保留既有基线是维护动作，不是正文套话；需要引用时提供真实链接，按影响范围同步受影响内容，不用增量说明覆盖或删除完整需求。
- 变更涉及关联页面时说明影响并同步对应规则，不复制整页旧需求。

### 表达示例

- 页面修改：“不再展示全部科目，不影响已购买课程，仅调整科目选择区域，其他逻辑保持不变。” → “科目选择区域仅展示用户已购买课程对应的科目。”
- 全新页面：“已确认：用户点击开始练习后直接进入答题页，不需要再进入其他中间页面。” → “用户点击‘开始练习’，进入答题页。”
- 匹配范围：“支持按正式名称及已维护的考试简称、别名匹配，例如输入‘教资’可找到‘教师资格证’；不自动猜测别名。” → “搜索匹配范围为考试正式名称及已维护的简称、别名，例如输入‘教资’可找到‘教师资格证’。”
- 展示内容：“右侧按考试分组展示匹配条目；条目仅使用正式名称，不附加结果数量、所属分类副标题或别名标签。点击条目进入对应考试。” → “右侧按考试分组展示匹配条目，条目仅显示考试正式名称；点击条目进入对应考试。”

## 5. 产品层表达边界

页面中不增加“原型说明”模块或“仅演示……”“不模拟……”等演示限制提示。真实的未实现功能和验证限制在交付说明或验收记录中如实列明；正常业务规则、用户提示及错误反馈保留。

默认不输出接口地址、请求响应结构、错误码、数据库、服务名、技术字段及类型、URL 或埋点参数、缓存策略和技术架构。

可以表达用户资格与权益、业务内容及缺失处理、操作结果、状态变化、恢复方式、业务时效，以及需要保留的来源、筛选或目标内容等业务上下文。

用户明确要求技术方案、接口或埋点时，作为独立任务处理，不混入产品需求正文。
